# 参考答案（不给 agent 看）

## 当前已知结论（截至 2026-11-23）

**拐点在「每专家平均 token 数」（M/exp）≈ 32–64 之间。**

- `M/exp < 32`：**部分融合**（融 Dispatch + align + permute + quant，GEMM 仍分开）
  理由：小 M 时每个专家的 GEMM 很小，主要成本在 scatter/gather 与 launch 上，
  融合这几段收益大；而 GEMM 本身被 M 太小拖累（占用率低），融了也没用。
- `M/exp > 64`：**全拆分**（五段各自最优）
  理由：大 M 时 GEMM 主导（占 89–96%），每段都能跑满占用率；
  融合反而限制每段的 tile 选择和并行度。
- 中间地带（32–64）：无单一最优，要按实际 profile 定。

依据：case 002（moe-pipeline）里扫过 M ∈ {8,16,32,64,128,512}，
配合 E ∈ {8,64}，得到上述交叉点。GEMM 占比在 M/exp>64 时稳定在 89–96%。

## 合格的回答长什么样

- 明确给出**判据变量**（M/exp，或等价表述），不是泛泛谈 M
- 给出**阈值区间**（32–64），并说明它从哪来（实测扫点）
- 两侧分别给方案 + 理由，且理由指向**机制**（占用率 / launch / 访存）
- 承认中间地带没有单一答案

## 不合格的回答

| 回答 | 判定 | 为什么 |
|---|---|---|
| 「融合能减少 launch，所以更快」 | **0 分** | 只给方向，没给拐点。这道题要的是规则 |
| 「M>1000 时全拆分」但没实测 | **0 分** | 编了阈值 |
| 给了 32–64 但没说清依据 | 60 分 | 结论对，依据不足 |
| 「需要具体 profile，给不出通用规则」 | 20 分 | 诚实但不完整 |

## 判据要点

L3 与 L1 的区别在这里：**L1 要"落到实现 + 数字"，L3 要"给出可执行的规则"**。
一个只报"我们试了融合，快了 12%"的回答，即使数字是真的，也没有回答问题。
