# 任务：all-reduce 该不该进算子卡体系

## 背景

我们有一套算子知识库（atlas 卡），每张卡描述一个算子：函数入口、形状约束、
达成率、坑。它现在的范围是**单卡上的计算算子**。

团队在讨论要不要把**通信原语**也纳进来。第一个候选是 all-reduce——
它在张量并行里无处不在，而且经常是瓶颈。

## 要回答的

**all-reduce 应该作为算子纳入这套体系吗？如果不该，正确的落点是什么？**

要求给出：

1. **结论**：应该 / 不应该，以及理由
2. **依据**：all-reduce 在本机实际由什么提供（查一下实现归属）、它的可调参数是什么
3. **边界**：如果结论是「不该」，那与通信相关的**性能问题**该由哪类卡片/哪一层承接
4. **复跑**：给出你跑的命令与脚本位置

## 约束

- 时间预算：**10 分钟**
- 只写你实际验证过的东西。**没验证的写「未验证」，不要推测成结论。**
- 产出写到当前目录的 `report.md`，验证脚本放 `scripts/`，原始输出放 `results/`。

## 评判标准

> 这道题考的是**分类判断**：哪些东西属于"算子卡"这个抽象，哪些不属于。
> 直接说"应该纳入，因为 all-reduce 很慢"视为没答到点上——慢不等于属于这个抽象。
