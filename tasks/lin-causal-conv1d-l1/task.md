# 任务：评估线性注意力里 causal conv1d 的带宽达成率

## 背景

我们在 8 卡 DCU（gfx938，Hygon BW1100）上跑线性注意力模型（GDN / Mamba 一类）。
这类模型没有 softmax，每一层开头是一段**因果短卷积**：

```
out[b, d, t] = sum_{k=0}^{W-1} weight[d, k] * x[b, d, t - (W-1) + k]      W = 4
```

也就是每个通道独立、只在时间轴上前看 3 步的 depthwise 卷积，序列开头补零。
它夹在投影和门控之间，每层都要跑一次，看起来很便宜——但它动的是整块
`[B, D, S]` 激活，没有任何可复用的规约。

团队现在想确认一件事：**这一段到底是「已经贴着硬件带宽上限」，还是「还有明显的
优化空间」？** 如果已经到顶，就不该在这上面花人力，而应该去优化别的段。

## 要回答的

**本机跑 causal conv1d（B×2048×S，bf16，width=4），带宽达成率是多少？还有多少空间？**

具体要给出：

1. **落到了哪个实现**：你实际调用的 `库.函数`、版本、**完整调用签名**
2. **实测耗时**：题面给出的每一个 S 都要有数字（不要只报最好看的那一个）
3. **流量口径**：这一段到底读了多少、写了多少字节，逐项列出并说明依据。
   特别要说清：重叠窗口和 causal 掩码（序列开头几个位置的窗口不满 W 个 tap）
   会怎样影响你对「实际从显存搬了多少」的估计。
4. **达成率**：分母取自哪里、为什么可信，为什么这个算子该用带宽口径而不是算力口径
5. **结论**：还有多少空间、下一步该动哪里（或者"已经到顶，别动"）
6. **复跑**：给出命令与脚本位置

## 约束

- 时间预算：**30 分钟**
- 只写你实际验证过的东西。**没验证的写「未验证」，不要推测成结论。**
- 计时必须用 GPU event（`torch.cuda.Event`），**不许用 wall clock** ——
  异步 kernel 用 `time.time()` 会被量成 0，小形状尤其明显。
- 每轮计时前要处理 L2 缓存（本机 L2 = 8 MB），否则热数据会把带宽虚高。
- **注意**：短序列（S 只有一两百）时，单次 kernel launch 的固定代价可能
  占掉很大一块。如果你的数字与流量上限差得很远，先分清是带宽不够还是
  launch 不够——两者的优化方向完全不同。
- 产出写到当前目录的 `report.md`，验证脚本放 `scripts/`，原始输出放 `results/`。

## 评判标准

> 这道题最容易错的地方不是计时，是**流量口径**。
>
> 卷积有重叠窗口、又有 causal 掩码，一个不小心就会把「逻辑上被用了几次」
> 和「实际从显存搬了几次」混为一谈。口径错一次，达成率就错——多算读或
> 少算写，都会让你得出「还有 N 倍空间」去优化一个不存在的问题，或者反过来
> 误判成「已经打满」。
>
> 你必须自己把这件事拆清楚：哪些是真正的 DRAM 流量、哪些只是片上复用或
> 被掩掉的计算，并在报告里给出依据。
>
> 另外：只报一个形状、拿最好看的那个说话，视为不足以支撑结论。
