# 参考答案（不给 agent 看）

## 语义

```
out[m, i, h] = post[m, i] * x[m, h]  +  Σ_{j=0}^{3} comb[m, i*4+j] * residual[m, j, h]
```

H=4096, HC=4。`comb` 行和 ≈1、非负（Sinkhorn 输出）；`post` 非负（sigmoid）。

## 流量

| 项 | 字节 | M=4096 |
|---|---|---|
| 读 `x` | `M*H*2` | 33.6 MB |
| 读 `residual` | `M*HC*H*2` | 134.2 MB |
| 写 `out` | `M*HC*H*2` | 134.2 MB |
| 读 `post` | `M*HC*4` | 0.065 MB |
| 读 `comb` | `M*NCMB*4` | 0.262 MB |
| **合计** | `M*H*2 + 2*M*HC*H*2 + ...` | **302.2 MB** |

每 token 9H = 73 728 字节。`post`/`comb` 合计 0.33 MB，占 0.1%，不构成可优化空间。

## 这题的判据：residual 被读几遍

输出有 4 个 i，每个 i 要 Σ over 4 个 j：

```
out[m,0,:]  ← res[m,0,:] res[m,1,:] res[m,2,:] res[m,3,:]
out[m,1,:]  ← res[m,0,:] res[m,1,:] res[m,2,:] res[m,3,:]
out[m,2,:]  ← res[m,0,:] res[m,1,:] res[m,2,:] res[m,3,:]
out[m,3,:]  ← res[m,0,:] res[m,1,:] res[m,2,:] res[m,3,:]
```

**4 行输出都需要全部 4 份 residual。**

| 分块方式 | residual 读几遍 | 总流量 |
|---|---|---|
| 按 i 分工（一个 CTA 算一个 i） | **4 遍** | 1H + 16H + 4H = **21H** |
| 一个 CTA 同时持有 4 个 i | **1 遍** | 1H + 4H + 4H = **9H** |

9H 是地板。21H 在 M=4096 时是 705 MB vs 302 MB，**2.3 倍的差距全在分块上**。

靠 L2 兜重复读**兜不住**：residual 在 M=1024 时就有 33.6 MB，本机 L2 只有 8 MB。
所以按 i 分工的实现会看到带宽随 M **非单调**（M 越小越吃亏），那不是 DPM 抖动。

### 为什么"按 i 分工"看起来也很自然

因为 `out` 的 4 个 i 是**并列**的，直觉上像 4 个独立任务可以扔给 4 个 CTA 并行。
错在没意识到它们的**输入完全相同**。这和 `moe-sum-l1`（沿 K 轴求和，一趟读完）
是同一类认知错误，只是那题只有 1 个输出，没机会犯错。

## 基线

`sglang.kernels.ops.layernorm.mhc.mhc_post_tilelang` —— sglang 自带的 tilelang
kernel，也是 GLM-5.3-Flash 服务实际走的路径。

**签名坑**：`mhc_post_tilelang(a, b, c, d, x, hc, hidden, n_thr=128, h_blk=1024)`，
第 5 个位置参数才是 output 缓冲区：

```python
mhc_post_tilelang(comb.view(-1,4,4), residual, post.squeeze(-1), x, out, 4, H)
#                 ↑ a=comb          ↑ b=res      ↑ c=post      ↑ d=x  ↑ x=out
```

参数名 `x` 被**重复使用**了两次（第 5 位是输出、第 4 位是输入 `x`），照着
kernel 的调用顺序 `(x, residual, post, comb, o, ...)` 抄会静默写错位置。

实测（M=4096，默认参数）：**462 µs / 653 GB/s**。

## 可优化空间

同一份 tilelang 实现，**只调 `n_thr`/`h_blk`**（不碰算法）：

| n_thr | h_blk | 耗时 | 带宽 |
|---|---|---|---|
| 128 | 1024 | 489 µs | 617 GB/s |
| 256 | 256 | **273 µs** | **1106 GB/s** |
| 256 | 1024 | 503 µs | 601 GB/s |
| 512 | 512 | 298 µs | 1014 GB/s |
| 512 | 1024 | 1679 µs | 180 GB/s |
| 默认 | 1024 | 462 µs | 653 GB/s |

**1.69 倍纯靠 launch 参数**。这个非单调性（512/1024 反而慢 3.6 倍）说明
tile 划分和 `h_blk=1024` 的整除关系不合——不是噪声。

> 注意：这组扫参是在**别的进程占着卡**时测的，绝对数值不可信（当时纯拷贝
> 只有 855 GB/s，远低于 constants 的 copy 峰值 1350）。**比例关系**可用，
> 复测必须重跑。这也是这题要考"分母从哪来"的原因之一。

自研 HIP 实现记录到 **1456–1827 GB/s**（`/workspace/mhc_kernels/RESULTS.md`），
即 78–98% 流式峰值。这说明 9H 口径下确实能贴到带宽墙。
