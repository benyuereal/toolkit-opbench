# 任务：评估 add + RMSNorm + SwiGLU 三段融合的达成率

## 背景

我们在 8 卡 DCU（gfx938，Hygon BW1100）上优化一个 Transformer block 的前半段。
这一段在真实模型里是**连着做三件事**的：

```python
h   = x + residual                       # ① 残差相加
h   = w * h / sqrt(mean(h²) + eps)       # ② RMSNorm
# 然后是 FFN 的门控：h 的宽度是 2*I，前半是 gate，后半是 up
g, u = h.chunk(2, dim=-1)
out  = silu(g) * u                       # ③ SwiGLU（silu-and-mul）
```

按标准写法，这三段是**分开跑的**（至少 2~3 个 kernel）。

| 张量 | 形状 | dtype |
|---|---|---|
| `x` | `[M, 4096]` | bf16 |
| `residual` | `[M, 4096]` | bf16 |
| `weight` | `[4096]` | bf16 |
| `out` | `[M, 2048]` | bf16 |

`H = 4096`、`I = 2048`、`eps = 1e-6` 固定；`M` 是变量，会出现多个档位。

团队现在的问题是：**这三段能不能合成更少的 kernel，能省多少？**

## 要回答的

**在本机，把「残差相加 + RMSNorm + SwiGLU」三段合起来算，
最快能做到多少？相对当前的分离实现能快多少？**

具体要给出：

1. **落到了哪个实现**：`库.函数`、版本、完整调用签名。
   如果是把多段拼起来，**写清拼了哪几段、各自是哪个函数**。
2. **实测耗时**：按 harness 下发的口径档位，写成 `results/bench_std.json`。
3. **有效流量**：这一段实际读写多少字节，怎么算的。
4. **达成率**：分母取自哪里、为什么可信。
5. **结论**：融合还有多少空间；如果不能融合到一步，说明卡在哪。
6. **复跑**：给出命令与脚本位置。

## 约束

- **时间预算：60 分钟**
- 只写你实际验证过的东西。**没验证的写「未验证」，不要推测成结论。**
- 计时必须用 GPU event（`torch.cuda.Event`），**不许用 wall clock**。
- 每轮计时前要处理 L2 缓存（本机 L2 = 8 MB）。
- **如果被测实现会原地改写输入**，每轮之间必须喂**独立副本**，
  否则第二轮起读到的是上一轮的结果。
- 产出写到当前目录的 `report.md`，脚本放 `scripts/`，原始输出放 `results/`。

## 正确性判定（硬门槛）

**输入输出对得上就算正确，不管用什么实现。**

上面那段伪代码是**参考公式**，用来对齐"这个算子在算什么"。
判定只看一件事：给定同样的输入，你的输出与参考实现在
**rtol = 0.05 / atol = 0.05** 内一致（bf16 精度下的合理容差）。

- 用哪个库、写 Triton、写 HIP、手写、几段拼接——**都不限**。
- 中间怎么算、按什么顺序算、是否复用缓冲区——**都不限**。
- 满足上面容差、shape 对、dtype 对，正确性就通过。

**流量公式也只是参考**，用来把耗时折算成达成率做横向比较。
你自己的流量算法与它不同不扣正确性分，只要在报告里写清你按什么算的。

## 评判标准

> 这道题有几个容易出错的地方：
>
> ① `eps` 在 sqrt **内**还是外：`sqrt(mean+eps)` vs `sqrt(mean)+eps`。写错数值对不上。
> ② gate/up 是沿**最后一维对半切**（前 I 是 gate），不是交错。
> ③ 输出宽度是 **I**（2048），不是 **2I**（4096）——两个半张量乘成一个。
>
> 只报「跑起来了、耗时 X」而不说清流量和融合程度的，视为结论不完整。
