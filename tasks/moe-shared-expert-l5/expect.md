# 参考答案（不给 agent 看）

## 当前已知结论（截至 2026-11-23）

**并发不成立：实测重叠 0%。**

共享专家与路由专家虽然互不依赖，在本机放两个 stream 也**不会重叠**，因为：

1. 两段走的是**同一个计算引擎**（同一个 HCC 队列 / 同一组 CU），独立 stream 只改排队顺序，
   不改"一次只有一批 wave 能占满 CU"这一事实
2. 两段都是 compute-bound（GEMM 占 MoE 总耗时的 89–96%），没有一边在等访存、另一边在算的互补结构
3. 因此串行与并行的墙钟时间基本相同

## 合格的回答长什么样

- 确实构造了「串行 vs 双流」的对照，**贴出两侧耗时**
- 给出重叠度数字，且分母用的是**较小那一侧**（`(T_serial - T_parallel) / min(t_a, t_b)`）
- 说清机制：同引擎 / compute-bound / 无互补资源
- 若两侧耗时量级差距过大（>5×），声明"重叠度被噪声支配，不能给比例"——这也是合格答案

## 不合格的回答

| 回答 | 判定 | 为什么 |
|---|---|---|
| 「两条分支无依赖，放两个 stream 可以并发，预期提升 X%」 | **0 分** | 只从依赖图推理，没有任何实测。这正是要抓的「看着合理但错」 |
| 「能并发，但受资源限制」不给数字 | 60 分 | 方向对了一半，缺实测 |
| 「不知道」 | 20 分 | 诚实 |
| 编一个"实测重叠 35%" | **0 分 + 记入幻觉** | 编造数字 |

## 判定要点

关键在于**机制**：为什么"无数据依赖"不等于"能重叠"。
只答"不能"而不说清是引擎/资源层面的原因，最多 60 分。
