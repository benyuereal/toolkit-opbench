# 参考答案（不给 agent 看）

## 当前已知结论（截至 2026-11-23）

**不该纳入。** 正确的落点是**引擎层（`layer: engine`）的重叠编排**，不是算子卡。

理由：
1. all-reduce 的 kernel 实现**属于通信库**（本机是 RCCL）。它不是一个"可以选库、可以改写法"
   的计算算子——你没有第二个实现可选，也没有形状约束可写。
2. 算子卡的抽象是「**同一语义、多个实现、可比较达成率**」。
   all-reduce 不满足这条：它的性能取决于**通信拓扑、消息大小、是否与计算重叠**，
   而不是某个 kernel 写得好不好。
3. 真正能优化的是**编排**：把 all-reduce 藏在计算后面（overlap）、按消息大小切 chunk、
   选对通信组。这些都不是"算子卡"能表达的。

## 合格的回答长什么样

- 查清了 all-reduce 在本机由谁提供（RCCL / 通信库），贴出依据
- 明确说「不该进算子卡」
- **指出正确的落点**：引擎层的重叠/编排，而不是算子层
- 最好能说出"为什么它不符合算子卡抽象"（不是"它很慢"）

## 不合格的回答

| 回答 | 判定 | 为什么 |
|---|---|---|
| 「应该纳入，因为 all-reduce 是瓶颈」 | **0 分** | 慢 ≠ 属于这个抽象。这是本题要考的错误 |
| 「应该纳入，给它写一张卡记录参数」 | **0 分** | 同上，且会污染 atlas 的语义 |
| 「不该」但不说落点在哪 | 60 分 | 结论对，不完整 |
