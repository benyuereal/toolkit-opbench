# 任务：评估 MoE gating（top-k softmax）的实现选型与耗时地板

## 背景

我们在 8 卡 DCU（gfx938）上优化 MoE 层。一层 MoE 的第一段是路由：

```
gating_output [M, E]  →  softmax  →  top-k  →  (weights, indices)
```

具体语义：

```
probs[m, :] = softmax(gating_output[m, :])                 沿最后一维
weights[m, :], indices[m, :] = topk(probs[m, :], k)        降序取 k 个
```

| 张量 | 形状 | dtype |
|---|---|---|
| `gating_output` | `[M, 64]` | fp32 |
| `topk_weights` | `[M, 8]` | fp32 |
| `topk_indices` | `[M, 8]` | int32 |

`E = 64`，`k = 8`，均固定；`M` 是变量，会出现多个档位。

两点容易对不上的地方，写出来免得你答错题：
- `topk_weights` 是 **softmax 后的原始概率**，不除以 top-k 之和（不做归一化）。
- top-k **在 softmax 之后**取，不是先取后 softmax。

团队要新写一个 gating 算子，问：**这一段该怎么实现，它的耗时下限在哪？**

这个问题的答案决定要不要投入：是继续优化这一段，还是把人力放到别处。

## 要回答的

**在本机，M×64 的 top-k softmax（k=8）这一段的耗时下限是什么？该选哪个实现？**

具体要给出：

1. **落到了哪个实现**：`库.函数`、版本、**完整调用签名**（按你实际调用到的写全）
2. **实测耗时**：至少两个 M 档位
3. **地板分析**：这一段的耗时相对「单次 kernel launch 的固定代价」是什么比例
4. **结论**：还有没有优化空间；这个结论受什么支配
5. **复跑**：给出命令与脚本位置

## 约束

- 时间预算：**30 分钟**
- 只写你实际验证过的东西。**没验证的写「未验证」，不要推测成结论。**
- 计时必须用 GPU event（`torch.cuda.Event`），**不许用 wall clock**。
- 小算子尤其要注意：如果用 Python 侧 `time.time()`，量到的主要是 Python 开销。
- 产出写到当前目录的 `report.md`，验证脚本放 `scripts/`，原始输出放 `results/`。

## 评判标准

> 这道题的关键判断是「值不值得优化」，不是「跑多快」。
>
> 达成率低不必然等于有优化空间——要先分清这个耗时由什么构成，
> 再看该不该动手。结论必须建立在你实测的数上，并说明你是怎么归因的。
