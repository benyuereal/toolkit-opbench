# 任务：MoE token 块对齐重排的耗时地板在哪

## 背景

我们在 8 卡 DCU（gfx938，Hygon BW1100）上优化 MoE 推理。MoE 的一层在做专家
GEMM 之前，必须先把 token **按专家重排**成块对齐的布局——否则 grouped GEMM
没法按固定 tile 高度切分。

这不是计算，是**纯数据搬运**：读一遍 token→专家的映射，产出三样东西。
看起来便宜，但每个 token 要选 K 个专家，映射表是 `M*K` 条，而且结果要落盘。

团队要确认：**这一段到底该不该继续优化？如果要，该往哪个方向动？**

## 算子定义

```
输入   topk_ids[M, K]         # 每个 token 选中的 K 个专家 id，取值 [0, E)
         E = 64, K = 8, ALIGN = 128

输出
  sorted_ids[CAP]             # 重排后的 token 下标（token*K + k）
  expert_ids[BLOCKS]          # 第 b 个块属于哪个专家
  num_post_pad[1]             # 前多少个 sorted_ids 是有效的

  CAP = M*K + E*ALIGN
  BLOCKS = CAP // ALIGN
```

规则：

1. 每个专家占用的 slot 数 pad 到 **ALIGN 的倍数**（各专家独立 pad，不能互借）。
2. `num_post_pad` = 所有专家 pad 后的 slot 总数。
3. `expert_ids[b]` = 第 b 个 ALIGN-slot 块所属的专家编号。
4. **只有前 `num_post_pad` 个 `sorted_ids` 有效**；之后是缓冲区内容，不参与判定。
5. 同一专家内部，token 的先后顺序**不作要求**（实现自行决定）。

| 张量 | 形状 | dtype |
|---|---|---|
| `topk_ids` | `[M, 8]` | int32 |
| `sorted_ids` | `[M*8 + 64*128]` | int32 |
| `expert_ids` | `[(M*8 + 64*128) / 128]` | int32 |
| `num_post_pad` | `[1]` | int32 |

`M` 是变量，会出现多个档位。

## 正确性判定（硬门槛）

**输入输出对得上就算正确，不管用什么实现。**

- 浮点容差对本算子无意义（全整数）：判据是**精确相等**。
- 但有两处**不算错**，不要因此改实现：
  - `sorted_ids` 的**顺序**不作要求（同一专家内部）。
  - `num_post_pad` 之后的内容不作要求。
- 除此之外必须精确匹配：`num_post_pad`、`expert_ids` 全段、
  `sorted_ids` 有效段里出现过的 token 集合。

## 要回答的

**在本机，这一段的耗时下限在哪？该选哪个实现？**

具体要给出：

1. **落到了哪个实现**：`库.函数`、版本、**完整调用签名**
2. **实测耗时**：题面给出的每个 M 档都要有数字
3. **有效流量**：这一段实际读写多少字节，怎么算的
4. **地板分析**：这一段的耗时由什么构成？相对「单次 kernel launch
   的固定代价」是什么比例？
5. **结论**：还有没有优化空间；如果有，该动的是哪一层
6. **复跑**：给出命令与脚本位置

## 约束

- **时间预算：30 分钟**
- 只写你实际验证过的东西。**没验证的写「未验证」，不要推测成结论。**
- 计时必须用 GPU event（`torch.cuda.Event`），**不许用 wall clock**。
- 每轮计时前要处理 L2 缓存（本机 L2 = 8 MB）。
- 产出写到当前目录的 `report.md`，脚本放 `scripts/`，原始输出放 `results/`。

## 评判标准

> 这道题的关键判断是「值不值得优化」，不是「跑多快」。
>
> 先算出这段数据搬一次到底要多久，再和你实测的耗时对比。
> 如果两者差出几十倍，说明瓶颈不在带宽上——那再优化访存是白费力气。
> 结论必须建立在你实测的数上，并说清你是怎么归因的。
>
> 另外：只报一个形状、拿最好看的那个说话，视为不足以支撑结论。
