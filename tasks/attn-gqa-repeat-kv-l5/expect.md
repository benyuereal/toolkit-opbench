# 参考答案（不给 agent 看）

## 当前已知结论（截至 2026-11-23）

**不该单独实现。** 理由三条：

1. `repeat_kv` 是**纯 broadcast**（`expand` + `reshape`），不产生数据拷贝。
   实测其耗时在 µs 量级，已被 kernel launch 地板（43 µs）完全支配。
2. 单独写一个"优化过的" kernel 只会**多一次 launch**，不可能比一个免费的视图操作更快。
3. 真正该做的是把它写进 `not_for`：**不要在算子清单里给它留位置**，
   否则会引导后续优化者去优化一个不存在的问题。

## 合格的回答长什么样

- 实测了 repeat_kv 的耗时（或指出它是视图操作、无需实测即可判定）
- 明确说「纯 broadcast / 视图 / 零拷贝」中的至少一种
- 把结论落成**规则**：「不该做」+ 理由，最好写出 `not_for` 形式的表述
- 给出替代：在 attention 内部直接消费原始 KV 形状，或用 `expand` 的视图语义

## 不合格的回答

| 回答 | 判定 | 为什么 |
|---|---|---|
| 「值得做，可以减少拷贝/可以和 attention 融合」 | **0 分** | 前提就错了：它本来就不拷贝 |
| 「给它写一个 fused kernel，预期提升 5%」 | **0 分** | 对不存在的问题做优化 |
| 「不需要，因为耗时很小」 | 60 分 | 结论对，但没说到"它根本不拷贝"这层 |

## 一个必须允许的例外

如果 agent 实测指出 `repeat_kv` 在**某个具体形状/实现下确实发生了真实拷贝**
并给出数据，以它为准。本题考的是「该不该做」，不是「背下答案」。
