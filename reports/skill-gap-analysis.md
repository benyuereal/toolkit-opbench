# toolkit-skills 的能力缺口分析

> 日期：2026-11-24 · 依据：三向对照实验（A 裸 / D SkillHub / C toolkit-skills）
> 场景：moe-gating · norm-fused-add-rmsnorm · mla-sparse

---

## 一句话结论

> **skill 让 agent 找到了正确的库，但没有让它把活干到最好。**
>
> 三个臂**都没有自主优化**，C 臂也一样。skill 现在的价值是"检索"，
> 不是"优化"——而业主的期望是后者。

---

## 一、核心证据：三臂都停在"测量"，没人"优化"

统计每个臂在每道题上是否写了自定义 kernel（`@triton.jit` / `.hip` / `hipcc`）：

| 题 | A（裸） | D（SkillHub） | C（toolkit-skills） |
|---|---|---|---|
| **moe-gating** | ✗ 无 | ✅ **写了 Triton**（`bench_triton.py`） | ✗ 无 |
| **norm** | ✅ **写了 Triton**（`ref2r2w.py`） | ✗ 无 | ✗ **无** |
| **mla-sparse** | ✗ 无 | ✗ 无 | ✗ 无 |

**C 臂（完整 skill）三道题一次都没写自定义 kernel。**

这是最刺眼的一条：**skill 越全，越倾向于"查现成的"，而不是"做得更好"。**

---

## 二、norm 这道题的完整对比

### 三臂落的实现

| 臂 | 实现 | 我统一实测 | 带宽 | 相对 |
|---|---|---|---|---|
| A | `lightop.fused_add_rms_norm` + **自写 Triton 对照** | 194.6 µs | 1379 GB/s | **100%** |
| D | `aiter.fused_add_rms_norm_cu` | 419.7 µs | 640 GB/s | **46%** |
| C | `lightop.fused_add_rms_norm` | 197.0 µs | 1363 GB/s | 99% |

**D 选错了实现（慢 2.2 倍）。A 和 C 都选了 lightop。**

### 但 A 和 C 的结论深度完全不同

**A 的结论**（有优化意识）：
> lightop 离带宽上限还有 **~17–22%**。这 17–22% 是**真实的 kernel 质量差距，
> 不是硬上限**：一个同样 2R+2W 语义、写法更简单的手写 Triton kernel 能到 **~90–94%**。

它**实际写了那个 Triton kernel 做对照**（`ref2r2w.py`）。

**C 的结论**（只有判断，没有行动）：
> 建议：**别为「换融合实现」再投入**。若 prefill 的 norm 占比可观，下一步是
> kernel 级占用率优化，预期收益上限 ~1.3×。

C 说了"下一步可以优化"，但**没有做**。

## 三、skill 里其实有答案，C 没用上

`toolkit_skills` 的 `op-rmsnorm-fused/ledger.md` 里有明确记录：

```
## 结论
1. lightop 真实值 ≈ 197 µs，不是 227.0。原记录高估 15.2%。
2. triton 慢约 20%（197 vs 242），不是 6.7%。
3. 三种实现全落在 1200~1380 GB/s，离纯 copy 可达 1749~1801 还有 22~39%。
```

C 实测出 **197.0 µs / 1363 GB/s**——**和 ledger 的记录完全一致**。

**所以 C 读到了这张卡，复现了数字，但没有执行卡里说的"还有 22~39% 空间"。**

## 四、moe-gating：skill 帮忙找到了库，但选错了实现

| 臂 | 落点 | 我统一实测 | 相对最优 |
|---|---|---|---|
| A | ❌ 声称"本 build 没有 fused top-k softmax" | 未测（脚本丢） | — |
| D | ✅ `aiter.ops.topk.grouped_topk` | 178.2 µs | 34% |
| C | ✅ `aiter.ops.topk.grouped_topk` | 178.2 µs | 34% |
| **参照** | `aiter.moe_c_topk_softmax` | **59.9 µs** | **100%** |

**D 和 C 都落到了正确的大方向，但选了一个慢 3 倍的实现。**

`grouped_topk` 是带专家分组的通用实现，有 group 开销；`moe_c_topk_softmax`
是纯 top-k softmax，这道题正好用它。

**skill 告诉了它们"有哪些函数"，但没告诉它们"这道题该用哪个"。**

## 五、mla-sparse：三臂都没优化（这题也确实没什么可优化）

| 臂 | 实现 | 实测 | 墙钟 |
|---|---|---|---|
| A | `flash_mla_sparse_fwd` | 461 µs (S=2048) | 1259s |
| D | 同上 | 497 µs | **419s** |
| C | 同上 | 500 µs | 578s |

**性能相同**（同一实现），因为这道题只有这一个专用 kernel。
三臂都通过了三个坑（topk 128 倍数 / 哨兵 / d_v=512），**都没尝试优化**。

这题是合理的——没有第二实现可选。但另外两题不是。

## 六、问题根因（按严重度排序）

### 🔴 P0：skill 只教"查"，不教"改"

**证据**：C 三道题零自写 kernel；A 在 norm 上写了，D 在 gating 上写了。

**根因**：skill 的结构是 `SKILL.md`（选型）+ `ledger.md`（历史实测）+ `candidates.yaml`（候选）。
**全是"选哪个"，没有"怎么改"**。当 agent 读完这些，它的行为就变成"挑一个现成的报数"。

**建议**：
1. 在每张卡的 `SKILL.md` 里加一节 **「如果你要超过现有实现，改哪里」**：
   具体到 tile 大小、向量化宽度、在途访存数、LDS 用量。
2. 加一条强制动作：**报完成率后，必须给出"下一个可尝试的优化"并写代码验证**，
   不能只写"建议下一步"。

### 🔴 P0：skill 推荐的实现不是最优

**证据**：
- moe-gating：skill 相关卡指向 `grouped_topk`（178µs），实际 `moe_c_topk_softmax` 是 59.9µs
- norm：D 臂（SkillHub）选了 `aiter.fused_add_rms_norm_cu`（419µs），`lightop` 是 197µs

**根因**：知识库记录"这个函数存在"，但没有**横向性能对比表**。

**建议**：
1. 每张卡加一节 **「本机所有可用实现的横向对比」**：函数名 + 实测耗时 + 测试条件。
2. 明确标注"**推荐实现**"和"**为什么**"（不只是"存在"）。
3. 对已安装的库做一次全量实测扫描，把结果写进卡里。

### 🟡 P1：ledger 里的结论没有变成行动指引

**证据**：`op-rmsnorm-fused/ledger.md` 写了"离 copy 上限还有 22~39%"，
C 复现了 197µs，但**没有尝试缩小这 22~39%**。

**根因**：ledger 是"历史记录"的语气（我们测过什么），不是"待办"的语气。

**建议**：在 ledger 顶部加一个 **「未完成的优化机会」** 区块，
列出每条已知的 gap + 具体的下一步动作 + 预期收益。

### 🟡 P1：skill 没说清"什么时候该自己写"

**证据**：三臂都在"选现成的"。但 moe-gating 上 `grouped_topk` 比
`moe_c_topk_softmax` 慢 3 倍，说明"现成的"不一定是"该用的"。

**建议**：在 `op-bench` 或顶层加一条判据：
```
如果 (最现成实现的达成率 < 60%) 且 (roofline 显示还有 >2× 空间)
  → 写自定义 kernel，不要停在"选型"
```

### 🟢 P2：三臂的计时口径不统一

**证据**：同一个 lightop 实现，B 报 606µs、C 报 203µs、我统一测 197µs。

**建议**：在 skill 里规定产物格式（`results/result.json` 的 schema），
包含 `shape` / `timing.method` / `sclk`。这也能让评测自动化。

---

## 七、给 skill 迭代的具体动作（按投入产出排序）

| # | 动作 | 预期效果 | 成本 |
|---|---|---|---|
| 1 | 每张卡加「本机所有实现横向对比表」 | 直接解决"选错实现"（moe-gating 慢 3 倍、norm D 慢 2.2 倍） | 中（每卡一次实测） |
| 2 | 每张卡加「要超过现有实现，改哪里」 | 直接解决"不自主优化" | 高（需要真实的优化知识） |
| 3 | ledger 顶部加「未完成的优化机会」 | 把历史结论变成待办 | 低 |
| 4 | 加"何时该自己写"的判据 | 防止"停在选型" | 低 |
| 5 | 规定产物格式 | 让评测可自动化 | 低 |

**第 1、3、4、5 条成本低、收益直接，建议先做。第 2 条是根本，但需要真金白银的优化经验。**

---

## 八、这个结论的局限

1. **n=2 题**（moe-gating + norm 有完整三臂），mla-sparse 三臂同实现无差异。方向可信，幅度不可信。
2. **C 臂的 norm 还在跑**（21:26），上面的 C 数据来自它的中间产物，最终报告可能补充内容。
3. **"没优化"可能部分是预算限制**：30 分钟里，先要理解问题、找实现、测量、写报告，
   剩下的时间不够写 kernel。**这不完全是 skill 的错，但 skill 应该帮它省下前面的时间。**
