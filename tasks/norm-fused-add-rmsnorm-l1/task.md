# 任务：评估 fused_add_rmsnorm 的带宽达成率

## 背景

我们在 8 卡 DCU（gfx938，Hygon BW1100）上优化推理栈。RMSNorm 在每层都会调用，
而且实际推理里它几乎从不单独出现——总是「残差相加 + RMSNorm」融在一起：

```
h = x + residual
y = h / sqrt(mean(h²) + eps) * g
```

第三段 `h` 还要往后传（给下一层做残差），所以这一段的**两个结果都要写出去**。

当前实现走的是未融合的三段式，团队怀疑它离带宽上限还很远，想换成融合实现。
需要先量化：**现在离上限多远，换了能省多少。**

## 要回答的

**本机跑 fused_add_rmsnorm（M×4096，bf16），带宽达成率是多少？还有多少空间？**

具体要给出：

1. **落到了哪个实现**：你实际调用的 `库.函数`、版本、签名
2. **实测耗时**：至少两个 M 档位（不要只报最好看的那一个）
3. **有效流量**：这一段的实际访存量是多少字节，你怎么算的
4. **达成率**：分母取自哪里、为什么可信
5. **结论**：还有多少空间、下一步该动哪里（或者"已经到顶，别动"）
6. **复跑**：给出命令与脚本位置

## 约束

- 时间预算：**30 分钟**
- 只写你实际验证过的东西。**没验证的写「未验证」，不要推测成结论。**
- 计时必须用 GPU event（`torch.cuda.Event`），**不许用 wall clock**。
- 每轮计时前要处理 L2 缓存（本机 L2 = 8 MB）。
- **注意**：如果被测实现会原地改写输入，每轮之间必须把输入恢复，
  否则第二轮起喂进去的是上一轮的结果，数字会越来越难看。
- 产出写到当前目录的 `report.md`，验证脚本放 `scripts/`，原始输出放 `results/`。

## 评判标准

> 这道题最容易错的地方不是计时，是**流量口径**。
>
> 算错流量，达成率就错：少算一份写，会把达成率虚高近一倍，得出"已经打满"；
> 多算一份，会得出"还有很大空间"去优化一个不存在的问题。
> 你必须自己把语义搞清楚——这段到底是几读几写——并在报告里说明依据。
>
> 另外：只报一个形状、拿最好看的那个说话，视为不足以支撑结论。
